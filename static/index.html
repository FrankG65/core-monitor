Was zeigt die Färbung nach Worker?What does coloring by worker show?
  • Jede Farbe steht für einen Worker-Prozess. Die Kacheln liegen in einer gemeinsamen Warteschlange; wer fertig ist, holt sich die nächste. So entsteht ein buntes, unregelmäßiges Muster.
  • Kacheln sind unterschiedlich rechenaufwendig: In der schwarzen Menge wird bis zur max. Iterationszahl gerechnet, außen ist oft nach wenigen Schritten Schluss. Worker mit aufwendigen Kacheln schaffen weniger davon – das zeigen die ungleich hohen Balken darunter.
  • Diese dynamische Verteilung gleicht die Last aus. Würde man das Bild starr in 48 gleich große Streifen teilen, müssten alle auf den Streifen mit dem meisten Schwarz warten.
  • Mit der Reihenfolge „aufwendige Kacheln zuerst“ siehst du beim Rendern, dass zuerst die Kacheln im schwarzen Inneren erscheinen und der Rand zuletzt. So bleibt am Ende keine lange Kachel übrig, auf die alle warten.
  • Beim Rechenverfahren C# stehen die Farben für Threads in einem einzigen Prozess statt für einzelne Prozesse.
  • Each color stands for one worker process. The tiles wait in a shared queue; whoever is done takes the next one. This creates a colorful, irregular pattern.
  • Tiles need different amounts of computation: inside the black set, every point runs up to the maximum iteration count, while outside it often stops after a few steps. Workers that get demanding tiles finish fewer of them – that is what the bars of unequal height below show.
  • This dynamic distribution balances the load. If you split the image rigidly into 48 equal strips, everyone would have to wait for the strip with the most black.
  • With the order “demanding tiles first” you can watch the tiles in the black interior appear first and the edge last. That way no long tile is left at the end for everyone to wait on.
  • With the computation method C#, the colors stand for threads in a single process instead of separate processes.

Wie lese ich das Diagramm – und warum nicht 48×?How do I read the chart – and why not 48×?

Die 13 RechenverfahrenThe 13 computation methods

  • Die Messwerte in dieser Erklärung stammen vom Referenzrechner (AMD Threadripper 3960X, 24 Kerne / 48 Threads, NVIDIA RTX 3090). Dieser Rechner: –. Eigene Werte liefert der Skalierungstest.
  • Beschleunigung = Zeit mit 1 Worker ÷ Zeit mit n Workern. Die gestrichelte Linie ist das Ideal (n Worker = n-mal so schnell), die blaue Linie das gemessene Ergebnis. Effizienz = Beschleunigung ÷ n.
  • Hauptbremse ist die Größe der Aufgabe, nicht SMT: Mit 48 Workern dauert ein Bild nur noch 0,3–1 s. Dann fallen der Leerlauf am Ende (die letzten, oft aufwendigen Kacheln laufen noch, die übrigen Worker warten) und die Verwaltung im Hauptprozess stark ins Gewicht. Gemessen: Bei 4-facher Arbeit (20 000 statt 5 000 Iterationen) steigt das Ergebnis mit 48 Workern von rund 18× auf rund 25×. Die CPU-Zeit aller Worker zusammen bleibt dabei fast gleich; verloren geht reine Wartezeit.
  • Ab 24 Workern teilen sich zwei Worker einen Kern (SMT). Für Mandelbrot macht das nur 5–8 % aus (siehe Heatmap-Erklärung). Der Knick bei 24 liegt deshalb vor allem daran, dass die Laufzeit dort schon sehr kurz ist.
  • Platzierung: Feste Bindung an Threads ändert wenig. „1 Thread je Kern zuerst“ war bei 8–16 Workern 5–10 % schneller als „Windows entscheidet“, bei 48 Workern sind alle Varianten gleich.
  • Reihenfolge „aufwendige Kacheln zuerst“: Vorab wird jede Kachel mit 8 × 8 Stichproben grob geschätzt (≈ 15 ms, in der Zeit enthalten). Die aufwendigen Kacheln mit viel Schwarz laufen dann zuerst, und am Ende bleiben nur kurze übrig. Das verkürzt den Leerlauf am Schluss: Mit 24–48 Workern wird es 10–20 % schneller (numba: 18× → 22×).
  • C# (.NET, echte Threads) rechnet bitgenau dasselbe Bild. Mit 1 Thread ist es genauso schnell wie numba, denn beide erzeugen fast gleichen Maschinencode. Der Vorteil liegt beim Drumherum: Start in 0,14 s statt 2–6 s für 48 Prozesse, gemeinsamer Speicher, keine Prozessgrenzen. Mit 48 Threads wird es 27× schneller.
  • C# + SIMD (AVX2) rechnet in jedem Thread 4 Pixel gleichzeitig: mit 1 Thread 3,7× schneller als ohne (1,65 s statt 6,1 s), ebenfalls bitgenau dasselbe Bild. Die relative Beschleunigung ist etwas kleiner (≈ 24× statt 27×), weil die Rechnung dann so kurz ist (0,07 s), dass Verwaltung und Datenübergabe stärker zählen und SMT weniger bringt (die Rechenwerke sind schon besser ausgelastet). Absolut ist es mit Abstand am schnellsten. Das zeigt die Ansicht „Laufzeit (s, logarithmisch)“.
  • Rust (echte Threads, ohne und mit SIMD) rechnet ebenfalls bitgenau dasselbe Bild und ist praktisch so schnell wie C#: Beide übersetzen in nahezu denselben Maschinencode. Mit 48 Threads und SIMD war Rust etwas schneller (0,062 s gegenüber 0,070 s), und es startet in 0,04 s (C#/.NET 0,14 s, Python-Pool mehrere Sekunden). Der große Sprung kommt also nicht von der Sprache, sondern von echten Threads und von SIMD.
  • C, C++ und Assembler (Visual Studio, /O2 /arch:AVX2 /fp:precise) liefern ebenfalls bitgenau dasselbe Bild und liegen innerhalb weniger Prozent bei C# und Rust: ohne SIMD alle bei ≈ 6,1 s (1 Thread) bzw. 0,22–0,24 s (48 Threads), mit SIMD bei ≈ 1,65 s bzw. 0,06–0,07 s.
  • Warum liegen die Sprachen so dicht beieinander? Die innere Schleife besteht aus wenigen Multiplikationen und Additionen, die jeder dieser Compiler (MSVC, LLVM bei Rust, RyuJIT bei C#, LLVM bei numba) in praktisch dieselben Maschinenbefehle übersetzt. Die Grenze setzt der Prozessor: Jeder Schritt muss auf das Ergebnis des vorigen warten. Unterschiede entstehen nur im Drumherum: Threads oder Prozesse, Start, Datenübergabe.
  • Was bringt Assembler? Der handgeschriebene AVX2-Kern (native/asm/kernel.asm, kommentiert) ist genauso schnell wie der Compiler, nicht schneller: Der Compiler erzeugt für so eine Schleife bereits optimalen Code. Mehr ginge nur mit Tricks, die in jeder Sprache gleich möglich sind: mehrere Pixelgruppen verschränkt rechnen, damit der Prozessor die Wartezeit füllt, FMA (ändert das Bild in der letzten Stelle) oder float statt double (8 statt 4 Pixel, aber ungenau beim Zoomen). AVX-512 hat dieser Prozessor nicht.
  • Kardioide/Kreis überspringen (klügerer Algorithmus): Punkte in der großen Kardioide und im Kreis links daneben liegen sicher in der Menge, das zeigt eine einfache Formel. Ohne Test laufen genau diese Punkte bis zur maximalen Iterationszahl, sie sind die rechenaufwendigsten im Bild. Das Bild bleibt exakt gleich (geprüft in allen Rechenverfahren, auch direkt an den Rändern). Gemessen bei 5000 Iterationen: Gesamtansicht mit 1 Thread 6–9× schneller, mit 48 Threads 2×; Zoom auf den Kardioiden-Rand bis 14×; Ausschnitte ohne Kardioide (Seepferdchental) unverändert. Mit vielen Threads ist der Gewinn kleiner, weil die übrige Arbeit ungleich verteilt und die Laufzeit sehr kurz wird. Ein besserer Algorithmus schlägt hier mehr Kerne: 1 Thread mit Test ist schneller als 8 Threads ohne.
  • GPU (Grafikkarte; gemessen mit einer RTX 3090) über einen Direct3D-Compute-Shader (native/gpu/mandel.hlsl): Jede der über 10 000 Recheneinheiten der Grafikkarte rechnet einen Bildpunkt. In float rechnet die GPU das Standardbild in ≈ 0,01 s, mit 20 000 Iterationen ≈ 5× schneller als die beste CPU (Rust SIMD, 48 Threads). Aber float ist ungenauer: In der Gesamtansicht weichen 0,3 % der Pixel ab, in tiefen Zooms 4–17 % (die Strukturen werden sichtbar anders). In double ist die GPU sogar langsamer als die CPU (0,2–0,4×), denn diese Grafikkarte rechnet double nur mit 1/64 der float-Geschwindigkeit. Auch dann weichen 0,01–0,5 % der Pixel ab: Der Grafiktreiber übersetzt den Shader auf eigene Weise, das lässt sich nicht vollständig steuern.
  • Bei der GPU braucht zusätzlich das Drumherum Zeit: Ergebnisse zurück zur CPU kopieren, auf der CPU einfärben, Bilddaten an den Server schicken. Auf der Seite braucht „GPU float“ deshalb ≈ 0,08 s statt der reinen 0,01–0,03 s. Die GPU-Last erscheint nicht in der Heatmap, die zeigt nur die CPU-Kerne (dort sieht man nur die kurze Einfärbung).
  • Beschleunigung oder Laufzeit? Die Beschleunigung vergleicht jede Variante nur mit sich selbst (1 Worker) und zeigt, wie gut sie skaliert. Welche Variante wirklich schneller ist, zeigt nur die Laufzeit.
  • Das Diagramm zeigt für jede Kombination aus Rechenverfahren, Platzierung und Reihenfolge den neuesten Lauf mit denselben Bildeinstellungen.
  • Der Prozessstart (rechte Spalte) ist nicht in den Zeiten enthalten. Er wird getrennt gemessen, weil der Pool bei normaler Nutzung bestehen bleibt.
  • The measurements in this explanation come from the reference machine (AMD Threadripper 3960X, 24 cores / 48 threads, NVIDIA RTX 3090). This computer: –. The scaling test gives you your own values.
  • Speedup = time with 1 worker ÷ time with n workers. The dashed line is the ideal (n workers = n times as fast), the blue line is the measured result. Efficiency = speedup ÷ n.
  • The main brake is the size of the task, not SMT: with 48 workers, one image takes only 0.3–1 s. At that point the idle time at the end (the last, often demanding tiles are still running while the other workers wait) and the bookkeeping in the main process weigh heavily. Measured: with 4 times the work (20,000 instead of 5,000 iterations), the result with 48 workers rises from about 18× to about 25×. The CPU time of all workers together stays almost the same; what is lost is pure waiting time.
  • From 24 workers on, two workers share one core (SMT). For Mandelbrot this costs only 5–8 % (see the heatmap explanation). The bend at 24 is therefore mainly because the run time there is already very short.
  • Placement: binding to fixed threads changes little. “1 thread per core first” was 5–10 % faster than “Windows decides” with 8–16 workers; with 48 workers all variants are equal.
  • Order “demanding tiles first”: beforehand, each tile is roughly estimated with 8 × 8 samples (≈ 15 ms, included in the time). The demanding tiles with a lot of black then run first, and only short ones are left at the end. This shortens the idle time at the end: with 24–48 workers it gets 10–20 % faster (numba: 18× → 22×).
  • C# (.NET, real threads) computes a bit-identical image. With 1 thread it is exactly as fast as numba, because both produce almost the same machine code. The advantage lies in everything around it: startup in 0.14 s instead of 2–6 s for 48 processes, shared memory, no process boundaries. With 48 threads it gets 27× faster.
  • C# + SIMD (AVX2) computes 4 pixels at once in each thread: with 1 thread 3.7× faster than without (1.65 s instead of 6.1 s), again a bit-identical image. The relative speedup is somewhat smaller (≈ 24× instead of 27×), because the computation is then so short (0.07 s) that bookkeeping and data transfer count more and SMT helps less (the execution units are already busier). In absolute terms it is by far the fastest. The “Run time (s, logarithmic)” view shows this.
  • Rust (real threads, without and with SIMD) also computes a bit-identical image and is practically as fast as C#: both compile to nearly the same machine code. With 48 threads and SIMD, Rust was slightly faster (0.062 s versus 0.070 s), and it starts in 0.04 s (C#/.NET 0.14 s, Python pool several seconds). So the big jump does not come from the language, but from real threads and from SIMD.
  • C, C++ and assembler (Visual Studio, /O2 /arch:AVX2 /fp:precise) also deliver a bit-identical image and are within a few percent of C# and Rust: without SIMD all at ≈ 6.1 s (1 thread) or 0.22–0.24 s (48 threads), with SIMD at ≈ 1.65 s or 0.06–0.07 s.
  • Why are the languages so close to each other? The inner loop consists of a few multiplications and additions, which each of these compilers (MSVC, LLVM for Rust, RyuJIT for C#, LLVM for numba) turns into practically the same machine instructions. The limit is set by the processor: each step has to wait for the result of the previous one. Differences only arise in everything around it: threads or processes, startup, data transfer.
  • What does assembler bring? The hand-written AVX2 kernel (native/asm/kernel.asm, commented) is exactly as fast as the compiler, not faster: for a loop like this the compiler already produces optimal code. More would only be possible with tricks that work equally well in any language: computing several pixel groups interleaved so the processor fills the waiting time, FMA (changes the image in the last digit) or float instead of double (8 instead of 4 pixels, but inaccurate when zooming). This processor does not have AVX-512.
  • Skip cardioid/bulb (smarter algorithm): points in the large cardioid and in the bulb to its left are certainly in the set; a simple formula shows this. Without the test, exactly these points run up to the maximum iteration count – they are the most demanding points in the image. The image stays exactly the same (checked in all computation methods, right at the edges too). Measured at 5000 iterations: full view 6–9× faster with 1 thread, 2× with 48 threads; zoom on the cardioid edge up to 14×; regions without the cardioid (Seahorse Valley) unchanged. With many threads the gain is smaller, because the remaining work is unevenly distributed and the run time becomes very short. A better algorithm beats more cores here: 1 thread with the test is faster than 8 threads without it.
  • GPU (graphics card; measured with an RTX 3090) via a Direct3D compute shader (native/gpu/mandel.hlsl): each of the graphics card's more than 10,000 compute units computes one pixel. In float the GPU computes the standard image in ≈ 0.01 s; with 20,000 iterations it is ≈ 5× faster than the best CPU (Rust SIMD, 48 threads). But float is less precise: in the full view 0.3 % of the pixels differ, in deep zooms 4–17 % (the structures look visibly different). In double the GPU is even slower than the CPU (0.2–0.4×), because this graphics card computes double at only 1/64 of its float speed. Even then 0.01–0.5 % of the pixels differ: the graphics driver compiles the shader in its own way, and that cannot be fully controlled.
  • With the GPU, everything around it takes extra time: copying results back to the CPU, coloring them on the CPU, sending image data to the server. On the page, “GPU float” therefore takes ≈ 0.08 s instead of the pure 0.01–0.03 s. The GPU load does not appear in the heatmap, which only shows the CPU cores (there you only see the short coloring step).
  • Speedup or run time? Speedup compares each variant only with itself (1 worker) and shows how well it scales. Only the run time shows which variant is really faster.

Was zeigt dieser Test – und warum wird es mit mehr Kernen kaum schneller?What does this test show – and why does it barely get faster with more cores?
  • Die Messwerte in dieser Erklärung stammen vom Referenzrechner (AMD Threadripper 3960X, 24 Kerne / 48 Threads, NVIDIA RTX 3090). Dieser Rechner: –. Eigene Werte liefert der Skalierungstest.
  • Der Ablauf hat vier Phasen. Nur die erste ist voll parallel: Die Summe der Chudnovsky-Reihe wird in so viele Blöcke geteilt, wie es Worker gibt, und jeder Worker rechnet seinen Block aus.
  • Zusammenführen: Die Teilergebnisse werden paarweise kombiniert, wie bei einem Turnier. In der ersten Runde arbeitet noch die Hälfte der Worker, dann ein Viertel, ein Achtel … und im Finale nur einer. Gerade dort sind die Zahlen aber am größten (Millionen Stellen), und eine einzelne riesige Multiplikation lässt sich mit GMP nicht auf mehrere Kerne aufteilen.
  • Wurzel und Division sowie die Umwandlung in Dezimalziffern sind je eine einzige große Rechnung und laufen komplett seriell, egal wie viele Kerne da sind.
  • Das ist das Amdahlsche Gesetz: Ist ein Anteil s der Arbeit seriell, wird es höchstens 1/s-mal schneller. Bei 10 Millionen Stellen brauchen allein Wurzel, Division und Umwandlung 2,7 von 8,3 s (ein Drittel). Dazu kommen die obersten, größten Multiplikationen beim Zusammenführen. Gemessen ist daher bei etwa 2,1× Schluss (24–32 Worker), mit 48 Workern wird es sogar wieder langsamer, weil mehr Blöcke mehr Zusammenführen bedeuten. Beim Mandelbrot ist praktisch nichts seriell, deshalb geht es dort bis 25×.
  • In der Heatmap sieht man das direkt: einen kurzen roten Streifen über viele Zeilen (Reihe), dann immer weniger Zeilen (Zusammenführen), und zuletzt sekundenlang nur noch eine einzige helle Zeile (Abschluss). Am besten mit 10 Millionen Stellen ausprobieren.
  • Prüfung: Das Ergebnis wird mit mpmath verglichen, einer unabhängigen Implementierung (bis 1 Million Stellen, darüber die ersten 1 Million). Gerechnet wird mit 20 Schutzstellen, damit die letzten angezeigten Stellen nicht durch Rundung verfälscht sind.
  • The measurements in this explanation come from the reference machine (AMD Threadripper 3960X, 24 cores / 48 threads, NVIDIA RTX 3090). This computer: –. The scaling test gives you your own values.
  • The computation has four phases. Only the first one is fully parallel: the sum of the Chudnovsky series is split into as many blocks as there are workers, and each worker computes its block.
  • Merging: the partial results are combined in pairs, like in a tournament. In the first round half of the workers are still busy, then a quarter, an eighth … and in the final only one. But that is exactly where the numbers are largest (millions of digits), and with GMP a single huge multiplication cannot be split across several cores.
  • Square root and division as well as the conversion to decimal digits are each one single large computation and run completely serially, no matter how many cores there are.
  • This is Amdahl's law: if a fraction s of the work is serial, it can get at most 1/s times faster. At 10 million digits, square root, division and conversion alone take 2.7 of 8.3 s (one third). On top of that come the topmost, largest multiplications during merging. As measured, it therefore tops out at about 2.1× (24–32 workers); with 48 workers it even gets slower again, because more blocks mean more merging. With Mandelbrot practically nothing is serial, which is why it goes up to 25× there.
  • In the heatmap you can see this directly: a short red stripe across many rows (series), then fewer and fewer rows (merging), and finally, for seconds, only one single bright row (final step). Best tried with 10 million digits.
  • Check: the result is compared with mpmath, an independent implementation (up to 1 million digits; beyond that, the first 1 million). The computation uses 20 guard digits so that the last displayed digits are not distorted by rounding.

Was sehe ich hier – und worauf sollte ich achten?What am I looking at – and what should I watch for?

Aufbau

  • Jede Zeile ist ein logischer Prozessor (Thread): oben Thread 0, unten Thread 47.
  • Zwei benachbarte Zeilen gehören zu einem physischen Kern. Das sind die beiden SMT-Threads („Hyper-Threading“): zwei Befehlsströme, die sich Rechenwerke und Cache eines Kerns teilen.
  • Je 6 Zeilen bilden eine L3-Gruppe (bei AMD „CCX“: 3 Kerne mit gemeinsamem L3-Cache), links beschriftet und durch Linien getrennt.
  • Jede Spalte ist eine Sekunde. Rechts ist jetzt, das Bild wandert nach links; nach 2 Minuten fällt es heraus.
  • Farbe = mittlere Auslastung des Threads in dieser Sekunde: dunkel 0 %, grün ≈ 35 %, orange ≈ 70 %, rot 100 %.

Typische Muster

  • Mandelbrot mit 48 Workern: ein schmaler, fast durchgehend roter senkrechter Streifen über alle Zeilen – alle Threads rechnen gleichzeitig. Dauert die Berechnung unter 1 s, ist der Streifen nur eine Spalte breit und oft nicht ganz rot, weil eine Spalte den Mittelwert einer ganzen Sekunde zeigt.
  • Wenige Worker (z. B. 4): nur einzelne Zeilen leuchten, dafür länger. Welche Zeilen, entscheidet Windows. Auf dem Referenzrechner (Threadripper 3960X) landeten 4 Worker in Tests meist dicht beieinander in einer CCX (z. B. Threads 24–27), also paarweise auf beiden Threads desselben Kerns, obwohl andere Kerne frei waren. Mit der Einstellung „Platzierung“ oben kannst du das gezielt steuern und in der Heatmap vergleichen: „1 Thread je Kern zuerst“ ergibt einzelne, über alle CCX verstreute Zeilen, „kompakt“ einen dichten Block von oben.
  • Skalierungstest: eine Treppe. Erst ein langer Balken in wenigen Zeilen (1 Worker), dann immer kürzere Blöcke über immer mehr Zeilen. Die rote Fläche (= Rechenarbeit) bleibt ungefähr gleich groß, sie wird nur auf mehr Threads verteilt.
  • Last-Generator mit Affinität: genau die gewählten Zeilen sind rot. Mit „1. Thread je Kern“ entsteht ein Zebramuster (jede zweite Zeile). Ohne Affinität wandert die Last zwischen den Zeilen, weil Windows Prozesse verschiebt.

Worauf achten

  • Ausgefranstes Ende eines Laufs: einige Zeilen werden früher dunkel als andere. Das ist Lastungleichgewicht: Am Schluss sind nur noch wenige Kacheln übrig, die übrigen Worker haben nichts mehr zu tun. Kacheln in der schwarzen Menge sind besonders rechenaufwendig, weil dort bis zur max. Iterationszahl gerechnet wird.
  • Beide Threads eines Kerns rot heißt: Zwei Worker teilen sich einen Kern. Bei Mandelbrot macht das überraschend wenig aus, gemessen nur 5–8 % pro Worker. Jeder Rechenschritt wartet auf das Ergebnis des vorigen, ein einzelner Thread lässt den Kern daher großteils warten, und der zweite Thread füllt diese Lücken. Bei anderen Aufgaben (z. B. speicherlastigen) kann das ganz anders aussehen.
  • Grüne Einzelpunkte im Ruhezustand sind andere Programme (Browser, Windows-Dienste) – das Grundrauschen.
  • Vergleich mit der Kernansicht oben: Sie zeigt denselben Messwert, aber nur den aktuellen Stand und die letzten 60 s je Thread; die Heatmap zeigt alle Threads und den zeitlichen Ablauf auf einen Blick.

Layout

  • Each row is one logical processor (thread): thread 0 at the top, thread 47 at the bottom.
  • Two adjacent rows belong to one physical core. These are the core's SMT threads (“Hyper-Threading”): instruction streams that share the execution units and cache of one core.
  • Every 6 rows form an L3 group (on AMD a “CCX”: 3 cores with a shared L3 cache), labeled on the left and separated by lines.
  • Each column is one second. Now is on the right, and the image moves to the left; after 2 minutes it drops out.
  • Color = average load of the thread in that second: dark 0 %, green ≈ 35 %, orange ≈ 70 %, red 100 %.

Typical patterns

  • Mandelbrot with 48 workers: a narrow, almost entirely red vertical stripe across all rows – all threads compute at the same time. If the computation takes less than 1 s, the stripe is only one column wide and often not fully red, because a column shows the average of a whole second.
  • Few workers (e.g. 4): only individual rows light up, but for longer. Windows decides which rows. On the reference machine (Threadripper 3960X), 4 workers in tests usually ended up close together in one CCX (e.g. threads 24–27), that is, in pairs on both threads of the same core, even though other cores were free. With the “Placement” setting above you can control this deliberately and compare in the heatmap: “1 thread per core first” gives single rows scattered across all CCXs, “compact” a dense block from the top.
  • Scaling test: a staircase. First a long bar in a few rows (1 worker), then ever shorter blocks across more and more rows. The red area (= computing work) stays roughly the same size; it is just spread across more threads.
  • Load generator with affinity: exactly the selected rows are red. “1st thread per core” gives a zebra pattern (every other row). Without affinity the load wanders between rows, because Windows moves processes around.

What to watch for

  • Frayed end of a run: some rows go dark earlier than others. That is load imbalance: at the end only a few tiles are left, and the other workers have nothing more to do. Tiles in the black set are especially demanding, because there the computation runs up to the maximum iteration count.
  • Both threads of a core red means: two workers share one core. For Mandelbrot this matters surprisingly little, measured only 5–8 % per worker. Each computation step waits for the result of the previous one, so a single thread leaves the core waiting most of the time, and the second thread fills these gaps. For other tasks (e.g. memory-heavy ones) this can look very different.
  • Single green dots at idle are other programs (browser, Windows services) – the background noise.
  • Comparison with the core view above: it shows the same measurement, but only the current value and the last 60 s per thread; the heatmap shows all threads and the timeline at a glance.

Server-Einstellung „auf allen Netzwerkkarten erreichbar“. Der Monitor nutzt das bewusst nicht, sondern nur 127.0.0.1.

API

Assembler (MASM)
Prozessorbefehle in lesbarer Form, von Hand geschrieben. MASM ist der Microsoft Macro Assembler. mehr ↗
„Aufwendige Kacheln zuerst“
Reihenfolge, bei der eine grobe Vorab-Schätzung die rechenaufwendigsten Kacheln an den Anfang stellt, damit am Ende keine lange Kachel allein übrig bleibt.
AVX-512
Nachfolger von AVX2 mit 512-Bit-Registern (8 double gleichzeitig). Der Threadripper 3960X hat es nicht; neuere Prozessoren teils schon. mehr ↗
AVX2
SIMD-Befehlssatz aktueller x86-Prozessoren; 256-Bit-Register fassen 4 Kommazahlen (double), also 4 Bildpunkte je Befehl. mehr ↗
base64
Verfahren, Binärdaten (hier Bildkacheln) als reinen Text zu verschicken; etwa ein Drittel größer als das Original. mehr ↗
Binary Splitting
Rechentrick, der die Reihenglieder paarweise zu großen Brüchen zusammenfasst; die Teilstücke lassen sich parallel berechnen, die letzte Division nicht. mehr ↗
bitgenau

C / C++
Klassische, maschinennahe Sprachen. Hier mit dem Microsoft-Compiler (MSVC) aus Visual Studio übersetzt. mehr ↗
C# / .NET
Programmiersprache und Laufzeitumgebung von Microsoft; echte Threads, Übersetzung in Maschinencode zur Laufzeit. mehr ↗
Cache (L1/L2/L3)
Schneller Zwischenspeicher im Prozessor. L1/L2 gehören je einem Kern, L3 teilen sich die Kerne eines CCX. mehr ↗
CCX (Core Complex)
Bei AMD-Zen-Prozessoren eine Gruppe von Kernen mit gemeinsamem L3-Cache; beim 3960X 8 CCX zu je 3 Kernen. Im Monitor „L3-Gruppe“. mehr ↗
Chudnovsky-Formel
Sehr schnell konvergierende Reihe für Pi: etwa 14 neue Stellen je Glied. mehr ↗
Compiler-Schalter /O2, /arch:AVX2, /fp:precise, /MT
Optimieren, AVX2-Befehle erlauben, Rechnung exakt wie geschrieben (kein FMA), Laufzeitbibliothek fest einbinden (keine Zusatz-DLLs nötig). mehr ↗
CPU-Affinität (Platzierung)
Festlegung, auf welchen Threads ein Prozess laufen darf. Damit testet der Monitor „1 Thread je Kern zuerst“ gegen „kompakt“. mehr ↗
Digitale Signatur (Code-Signatur)
Elektronische Unterschrift eines Herstellers an einer .exe; signierte, verbreitete Programme lösen seltener Warnungen aus. Die Programme des Kern-Monitors sind nicht signiert. mehr ↗
Direct3D 11 Compute-Shader / HLSL
Programm, das auf der Grafikkarte läuft; geschrieben in HLSL, gestartet über Direct3D 11 (funktioniert mit jeder aktuellen Grafikkarte unter Windows). mehr ↗
double / float
Kommazahlen mit doppelter (≈ 16 Stellen) bzw. einfacher Genauigkeit (≈ 7 Stellen) nach IEEE 754. Spiele-Grafikkarten sind mit float viel schneller. mehr ↗
DXGI
Windows-Schnittstelle, über die der Monitor die vorhandenen Grafikkarten und ihren Speicher erkennt. mehr ↗
Embedded Python
Offizielles, schlankes Python zum Mitgeben in einem Ordner, ohne Installation. Steckt im Paket „Komplett“. mehr ↗
FastAPI / uvicorn
Python-Bausteine für den Webserver: FastAPI beschreibt die Schnittstellen, uvicorn liefert sie aus. mehr ↗
Fehlalarm (False Positive)
Ein Virenscanner hält ein harmloses Programm für gefährlich, weil es sich ähnlich verhält wie Schadsoftware (z. B. unsignierte .exe, volle Auslastung aller Kerne). Siehe „Hinweis zum Virenscanner“. mehr ↗
FMA (Fused Multiply-Add)
Multiplikation und Addition in einem Schritt mit nur einer Rundung. Schneller, verändert aber die letzte Stelle – und damit einzelne Bildpunkte. mehr ↗
GIL (Global Interpreter Lock)
Sperre im Standard-Python: Nur ein Thread führt gleichzeitig Python-Code aus. Deshalb nutzt der Monitor für Python Prozesse statt Threads. mehr ↗
gmpy2 / GMP
Bibliothek für sehr große Zahlen mit beliebig vielen Stellen; Grundlage der Pi-Berechnung. mehr ↗
GPU (Grafikkarte)
Prozessor mit Tausenden einfacher Recheneinheiten; ideal, wenn sehr viele gleichartige Rechnungen anfallen (z. B. je Bildpunkt eine). mehr ↗
Heatmap
Farbige Kachelansicht: je Thread ein Feld, Farbe = aktuelle Auslastung. mehr ↗
Intrinsics
Funktionen in C/C++/Rust, die direkt einem Prozessorbefehl (z. B. AVX2) entsprechen; SIMD ohne Assembler. mehr ↗
Iterationen (max_iter)
Wie oft z → z² + c höchstens wiederholt wird. Mehr Iterationen = feinere Ränder, aber mehr Rechenzeit (besonders im schwarzen Inneren).
JIT (Just-in-time-Übersetzung)
Code wird erst während des Programmlaufs in Maschinencode übersetzt; der erste Aufruf dauert daher länger. mehr ↗
JSON / CSV
Textformate für Messdaten: JSON für strukturierte Daten (eine Datei je Messung), CSV als Tabelle, die z. B. Excel öffnen kann. mehr ↗
Kachel
Rechteckiger Bildausschnitt (Standard 128 × 128 Pixel), die kleinste Arbeitseinheit eines Workers.
Kardioide und Periode-2-Kreis
Die herzförmige Hauptfläche und der große Kreis links davon gehören sicher zur Mandelbrot-Menge. Eine kurze Formel erkennt diese Punkte, ohne sie bis zur Höchstzahl durchzurechnen. mehr ↗
Kern (Prozessorkern)
Eigenständiges Rechenwerk im Prozessor. Der Threadripper 3960X hat 24 Kerne. mehr ↗
Lastverteilung (dynamisch)
Wer mit seiner Kachel fertig ist, holt sich die nächste. So bleiben keine Kerne untätig, obwohl Kacheln unterschiedlich lange dauern. mehr ↗
Mandelbrot-Menge
Bekanntes Fraktal: Für jeden Bildpunkt wird z → z² + c wiederholt, bis der Wert „entkommt“ oder die Höchstzahl erreicht ist. Jeder Punkt ist unabhängig – ideal für Parallelisierung. mehr ↗
Median
Mittlerer Wert einer sortierten Messreihe; unempfindlicher gegen Ausreißer als der Durchschnitt. Wird bei mehreren Läufen gewertet. mehr ↗
mpmath
Python-Bibliothek für Rechnen mit beliebiger Genauigkeit; dient als unabhängige Gegenprobe für die Pi-Stellen. mehr ↗
NUMA
Non-Uniform Memory Access: Bei großen Systemen ist Speicher je nach Kern unterschiedlich schnell erreichbar. Der 3960X hat einen NUMA-Knoten. mehr ↗
numba
Übersetzt ausgewählte Python-Funktionen beim ersten Aufruf in Maschinencode (JIT) und macht sie so etwa so schnell wie C. mehr ↗
numpy
Python-Bibliothek für Rechnen mit ganzen Zahlenfeldern (Arrays). Schnell bei einfachen Feldoperationen, aber nicht ideal für Mandelbrot. mehr ↗
OpenBLAS
Mathe-Bibliothek in numpy, die selbst Threads startet. Im Monitor auf 1 Thread je Prozess begrenzt, sonst braucht jeder Worker ~800 MB. mehr ↗
pip
Paketverwaltung von Python; installiert Erweiterungen wie numba oder FastAPI. mehr ↗
ProcessPoolExecutor
Python-Baustein, der einen Vorrat an Worker-Prozessen verwaltet und Aufgaben an sie verteilt. mehr ↗
Prozess
Laufendes Programm mit eigenem Speicher. Mehrere Prozesse laufen unabhängig, tauschen Daten aber nur über Umwege aus. mehr ↗
Prozessorgruppe
Windows fasst höchstens 64 Threads zu einer Gruppe zusammen. Prozessoren mit mehr Threads haben mehrere Gruppen; ein Prozess läuft normalerweise nur in einer. mehr ↗
psutil
Python-Bibliothek, die Auslastung, Speicher und Prozesse abfragt; liefert die Werte für die Kern-Anzeige. mehr ↗
Python
Verbreitete Skriptsprache; hier für Webserver, Steuerung und zwei Rechenverfahren. mehr ↗
Quarantäne
Abgeschotteter Bereich des Virenscanners für verdächtige Dateien; von dort lassen sie sich wiederherstellen. mehr ↗
Rust
Moderne Systemsprache mit C-ähnlicher Geschwindigkeit; der Übersetzer verhindert typische Fehler beim Arbeiten mit Threads. mehr ↗
rustup / cargo
rustup installiert und aktualisiert Rust; cargo übersetzt Rust-Programme und lädt benötigte Bibliotheken. mehr ↗
Scheduler
Teil von Windows, der entscheidet, welcher Thread wann auf welchem Kern läuft (Platzierung „Windows entscheidet“). mehr ↗
Seepferdchental
Bekannter Ausschnitt der Mandelbrot-Menge zwischen Hauptfläche und Periode-2-Kreis; sehr fein verästelt und daher rechenaufwendig. mehr ↗
Self-contained Single-File
.NET-Programm, das die Laufzeitumgebung in einer einzigen .exe mitbringt; läuft ohne installiertes .NET. mehr ↗
SIMD
Single Instruction, Multiple Data: Ein Befehl rechnet mehrere Zahlen gleichzeitig. mehr ↗
Skalierung, Beschleunigung, Effizienz
Beschleunigung = Zeit mit 1 Worker ÷ Zeit mit n Workern. Effizienz = Beschleunigung ÷ n (100 % = perfekt). mehr ↗
SmartScreen
Windows-Schutz, der vor unbekannten, nicht signierten Programmen warnt („Der Computer wurde durch Windows geschützt“). mehr ↗
SMT (Simultaneous Multithreading, bei Intel „Hyper-Threading“)
Ein Kern bearbeitet zwei Befehlsströme gleichzeitig und füllt damit Lücken in seinen Rechenwerken. Bringt meist 0–30 %, nicht 100 %. mehr ↗
Thread (Hardware-Thread, logischer Prozessor)
Was Windows als „CPU“ zählt. Mit SMT bietet jeder Kern 2 Threads, also 48 beim 3960X. mehr ↗
Thread (Software)
Ausführungsstrang innerhalb eines Prozesses; alle Threads teilen sich den Speicher und starten viel schneller als Prozesse. mehr ↗
vcomp140.dll / OpenMP
OpenMP ist ein Standard, mit dem C/C++-Programme Schleifen auf Threads verteilen; vcomp140.dll ist Microsofts Laufzeitbibliothek dafür und liegt dem Paket bei. mehr ↗
Vector256
.NET-Datentyp für ein 256-Bit-Register (4 double); damit nutzt C# AVX2. mehr ↗
VirusTotal
Kostenloser Dienst, der eine Datei mit rund 70 Virenscannern gleichzeitig prüft. mehr ↗
Visual Studio Build Tools
Microsofts Compiler für C, C++ und Assembler ohne die volle Entwicklungsumgebung; kostenlos. mehr ↗
WebSocket
Dauerhafte Verbindung zwischen Browser und Server; darüber kommen die Auslastungswerte jede Sekunde ohne Neuladen. mehr ↗
winget
Paketverwaltung von Windows; installiert Programme wie Python, .NET oder Rust per Befehlszeile. mehr ↗
Worker
Ein Prozess oder Thread, der Kacheln abarbeitet. Die Worker-Zahl stellt man im Monitor ein (1–48).

64-Bit-Befehlssatz der heutigen Intel- und AMD-Prozessoren (auch x86-64 oder AMD64). mehr ↗

0.0.0.0
Server setting "reachable on all network adapters". The monitor deliberately does not use it, only 127.0.0.1.
127.0.0.1 (localhost)
Address of your own PC. The server listens only there and is therefore not reachable from other computers. more ↗
Amdahl's law
The part of a program that cannot run in parallel limits the possible speedup, no matter how many cores are used (see Pi). more ↗
API
Interface through which the page (or a script) controls the server, e.g. /api/mandel/start. more ↗
Assembler (MASM)
Processor instructions in readable form, written by hand. MASM is the Microsoft Macro Assembler. more ↗
AVX-512
Successor of AVX2 with 512-bit registers (8 doubles at once). The Threadripper 3960X does not have it; some newer processors do. more ↗
AVX2
SIMD instruction set of current x86 processors; 256-bit registers hold 4 floating-point numbers (double), i.e. 4 pixels per instruction. more ↗
base64
Method to send binary data (here image tiles) as plain text; about one third larger than the original. more ↗
Binary splitting
Technique that combines the series terms pairwise into large fractions; the parts can be computed in parallel, the final division cannot. more ↗
Bit-identical
Every byte of the result is identical – here: 0 pixels difference between the computation methods.
C / C++
Classic languages close to the hardware. Compiled here with the Microsoft compiler (MSVC) from Visual Studio. more ↗
C# / .NET
Programming language and runtime from Microsoft; real threads, compiled to machine code at run time. more ↗
Cache (L1/L2/L3)
Fast buffer memory inside the processor. L1/L2 belong to one core, L3 is shared by the cores of a CCX. more ↗
Cardioid and period-2 bulb
The heart-shaped main area and the large disc to its left certainly belong to the Mandelbrot set. A short formula detects these points without iterating them up to the maximum. more ↗
CCX (Core Complex)
On AMD Zen processors a group of cores sharing one L3 cache; the 3960X has 8 CCXs with 3 cores each. Called "L3 group" in the monitor. more ↗
Chudnovsky formula
Very fast converging series for Pi: about 14 new digits per term. more ↗
Compiler switches /O2, /arch:AVX2, /fp:precise, /MT
Optimise, allow AVX2 instructions, compute exactly as written (no FMA), link the runtime library statically (no extra DLLs needed). more ↗
Core (processor core)
Independent execution unit inside the processor. The Threadripper 3960X has 24 cores. more ↗
CPU affinity (placement)
Defines on which threads a process may run. The monitor uses it to compare "1 thread per core first" with "compact". more ↗
"Demanding tiles first"
Order in which a rough up-front estimate puts the most compute-intensive tiles first, so that no long tile is left running alone at the end.
Digital signature (code signing)
Electronic signature of a publisher on an .exe; signed, widely used programs trigger warnings less often. The programs of Core Monitor are not signed. more ↗
Direct3D 11 compute shader / HLSL
Program that runs on the graphics card; written in HLSL, launched via Direct3D 11 (works with any current graphics card on Windows). more ↗
double / float
Floating-point numbers with double (≈ 16 digits) or single precision (≈ 7 digits) according to IEEE 754. Gaming graphics cards are much faster with float. more ↗
DXGI
Windows interface the monitor uses to detect the installed graphics cards and their memory. more ↗
Embedded Python
Official, lean Python distribution that can be shipped in a folder without installation. Included in the "Full" package. more ↗
False positive
Antivirus software considers a harmless program dangerous because it behaves similarly to malware (e.g. unsigned .exe, full load on all cores). See "Note on antivirus software". more ↗
FastAPI / uvicorn
Python building blocks of the web server: FastAPI describes the interfaces, uvicorn serves them. more ↗
FMA (fused multiply-add)
Multiplication and addition in one step with a single rounding. Faster, but changes the last digit – and thus individual pixels. more ↗
GIL (Global Interpreter Lock)
Lock in standard Python: only one thread executes Python code at a time. That is why the monitor uses processes instead of threads for Python. more ↗
gmpy2 / GMP
Library for very large numbers with any number of digits; the basis of the Pi computation. more ↗
GPU (graphics card)
Processor with thousands of simple execution units; ideal when a huge number of identical calculations is needed (e.g. one per pixel). more ↗
Heat map
Coloured tile view: one field per thread, colour = current load. more ↗
Intrinsics
Functions in C/C++/Rust that map directly to one processor instruction (e.g. AVX2); SIMD without assembler. more ↗
Iterations (max_iter)
The maximum number of times z → z² + c is repeated. More iterations = finer edges, but more computing time (especially in the black interior).
JIT (just-in-time compilation)
Code is compiled to machine code only while the program runs; the first call therefore takes longer. more ↗
JSON / CSV
Text formats for measurements: JSON for structured data (one file per measurement), CSV as a table that e.g. Excel can open. more ↗
Load balancing (dynamic)
Whoever finishes a tile fetches the next one. No core sits idle even though tiles take different amounts of time. more ↗
Mandelbrot set
Famous fractal: for every pixel z → z² + c is repeated until the value "escapes" or the maximum count is reached. Every point is independent – ideal for parallelisation. more ↗
Median
Middle value of a sorted series of measurements; less sensitive to outliers than the average. Used when several runs are made. more ↗
mpmath
Python library for arbitrary-precision arithmetic; serves as an independent cross-check of the Pi digits. more ↗
NUMA
Non-Uniform Memory Access: on large systems memory is reached at different speeds depending on the core. The 3960X has one NUMA node. more ↗
numba
Compiles selected Python functions to machine code on first call (JIT), making them about as fast as C. more ↗
numpy
Python library for computing with whole arrays of numbers. Fast for simple array operations, but not ideal for Mandelbrot. more ↗
OpenBLAS
Math library inside numpy that starts its own threads. Limited to 1 thread per process in the monitor, otherwise every worker needs ~800 MB. more ↗
pip
Python's package manager; installs extensions such as numba or FastAPI. more ↗
Process
A running program with its own memory. Processes run independently but can exchange data only indirectly. more ↗
Processor group
Windows combines at most 64 threads into one group. Processors with more threads have several groups; a process normally runs in only one. more ↗
ProcessPoolExecutor
Python building block that manages a pool of worker processes and distributes tasks to them. more ↗
psutil
Python library that queries load, memory and processes; supplies the values for the core display. more ↗
Python
Widely used scripting language; used here for the web server, control logic and two computation methods. more ↗
Quarantine
Isolated area of the antivirus software for suspicious files; they can be restored from there. more ↗
Rust
Modern systems language with C-like speed; its compiler prevents typical mistakes when working with threads. more ↗
rustup / cargo
rustup installs and updates Rust; cargo builds Rust programs and downloads the libraries they need. more ↗
Scaling, speedup, efficiency
Speedup = time with 1 worker ÷ time with n workers. Efficiency = speedup ÷ n (100 % = perfect). more ↗
Scheduler
Part of Windows that decides which thread runs on which core and when (placement "Windows decides"). more ↗
Seahorse valley
Well-known region of the Mandelbrot set between the main cardioid and the period-2 bulb; very finely branched and therefore compute-intensive. more ↗
Self-contained single file
.NET program that carries the runtime inside a single .exe; runs without an installed .NET. more ↗
SIMD
Single Instruction, Multiple Data: one instruction processes several numbers at once. more ↗
SmartScreen
Windows protection that warns about unknown, unsigned programs ("Windows protected your PC"). more ↗
SMT (simultaneous multithreading, Intel: "Hyper-Threading")
One core runs two instruction streams at once and fills gaps in its execution units. Usually gains 0–30 %, not 100 %. more ↗
Thread (hardware thread, logical processor)
What Windows counts as a "CPU". With SMT every core offers 2 threads, i.e. 48 on the 3960X. more ↗
Thread (software)
Execution path inside a process; all threads share the memory and start much faster than processes. more ↗
Tile
Rectangular part of the image (default 128 × 128 pixels), the smallest unit of work for a worker.
vcomp140.dll / OpenMP
OpenMP is a standard that lets C/C++ programs distribute loops across threads; vcomp140.dll is Microsoft's runtime library for it and is included in the package. more ↗
Vector256
.NET data type for a 256-bit register (4 doubles); this is how C# uses AVX2. more ↗
VirusTotal
Free service that checks a file with about 70 antivirus engines at once. more ↗
Visual Studio Build Tools
Microsoft's compilers for C, C++ and assembler without the full development environment; free of charge. more ↗
WebSocket
Permanent connection between browser and server; the load values arrive through it every second without reloading. more ↗
winget
Windows package manager; installs programs such as Python, .NET or Rust from the command line. more ↗
Worker
A process or thread that works through tiles. The number of workers is set in the monitor (1–48).
x64
64-bit instruction set of today's Intel and AMD processors (also called x86-64 or AMD64). more ↗
